# 报文夹具：怎么抓、怎么用

协议实现最危险的失败方式不是崩溃，而是**静默地读出错误的值**。字节序错了、
填充字节漏了、长度单位当成位而不是字节——这些错误在现场表现为"偶尔读到脏数据"，
是最难查的一类问题，而且往往在跑了两个月之后才被发现。

夹具就是防这个的：把真实报文存成文件，让每次改动都必须逐字节对得上。

## 现状

`tests/Rung.Protocols.S7.Tests/Fixtures/` 下所有夹具的 `source` 都是 `spec` ——
按协议规范推导出来的，不是真机抓的。

这意味着它们**能**做到：

- 移植协议代码时改错任何偏移量，测试立刻变红
- 重构传输层、引入 `Span` 优化时，行为不变得到保证
- 新人接手时，用报文本身说明每个字段的含义

**不能**做到：

- 证明西门子真机认这份请求
- 证明真机的应答就长这样

这个区分很重要，不要把 106 个绿灯当成"协议已经对了"。

## 拿到真机后要做的事（大约半小时）

### 1. 抓包

网关和 PLC 之间接一台能抓包的机器，或直接在网关上抓：

```bash
sudo tcpdump -i any -w s7.pcap 'tcp port 102'
```

跑一遍 Rung 的连接 + 采集，让它至少完成：COTP 握手、通讯建立、
一次单点读、一次多点读（含奇数长度的点位）、一次写。

### 2. 导出报文

Wireshark 打开 `s7.pcap`，过滤 `s7comm || cotp`，选中一个包，
右键 → Copy → …as a Hex Dump，或者用命令行：

```bash
tshark -r s7.pcap -Y 's7comm' -T fields -e tcp.payload
```

### 3. 替换夹具

把十六进制粘进对应的 `.hex` 文件，改掉头部两行：

```
# source:    capture
# device:    S7-1200 CPU 1214C DC/DC/DC, 固件 4.5.1
```

**测试代码一行都不用改。** 夹具是纯数据，加载器只认十六进制字符。

### 4. 收紧断言

`FixtureIntegrityTests.夹具都标明了来源` 目前接受 `spec` 和 `capture` 两种值。
全部换成真机夹具之后，把 `AllowedSources` 改成只允许 `capture`，
以后再有人加 `spec` 夹具就会被拦下来。

## 值得优先补的几份

按"错了最难查"排序：

| 场景 | 为什么重要 |
|---|---|
| 多点读，点位长度有奇有偶 | 填充字节规则只在这种组合下才暴露 |
| 跨 PDU 上限的大批量读 | 切分逻辑的边界，`MaxReadBytes` 的实际值需要真机确认 |
| REAL 类型读回 | 字节序的唯一权威依据。四种排列都可能出现 |
| S7-1500 的优化 DB 访问 | 与 S7-300 行为不同，是移植实现最容易失效的地方 |
| DB 号不存在时的应答 | 单点失败不能拖垮整批，这条路径必须有真实样本 |

## 夹具文件格式

```
# name:      简短标识，与文件名一致
# source:    spec | capture
# direction: request | response
# device:    仅 capture 需要，写明型号和固件版本
# note:      这份报文想固定住什么行为
03 00 00 1f  02 f0 80
32 01 00 00  00 02 00 0e  00 00
```

`#` 起注释，正文只认十六进制字符，空格换行随便排。
